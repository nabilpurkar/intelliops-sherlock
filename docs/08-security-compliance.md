# Security & Compliance Guide

> **What you'll learn:** Every security layer in this platform, why each layer exists, how they work together to implement defense-in-depth, and how to explain the security posture to a regulator or auditor.

---

## Defense-in-Depth Architecture

Security is not one tool — it's layered controls. If one layer is bypassed, the next catches it:

```
Layer 1: Development (before commit)
  └── Developer writes code → pre-commit hooks for secrets

Layer 2: CI Pipeline (before build)
  ├── GitLeaks: secret scanning
  ├── Semgrep SAST: code vulnerabilities
  ├── Trivy/OWASP SCA: dependency CVEs
  └── Checkov/tfsec/Conftest: IaC misconfigurations

Layer 3: Build (during image creation)
  ├── Hadolint: Dockerfile security
  ├── Trivy: base image CVEs
  ├── Grype + Syft: SBOM + second CVE scan
  └── Cosign: image signing (tamper-evident)

Layer 4: Admission (before pod starts)
  ├── Kyverno: 7 enforced policies
  ├── OPA Gatekeeper: constraint framework
  └── Cosign verification: image signature check

Layer 5: Runtime (while running)
  ├── Falco: kernel-level threat detection
  ├── Linkerd mTLS: all network encrypted + authenticated
  └── securityContext: non-root, read-only filesystem, dropped capabilities

Layer 6: Network (traffic between services)
  ├── Kubernetes NetworkPolicy: namespace isolation
  ├── Linkerd mTLS: mutual authentication
  └── Kong: API gateway with rate limiting

Layer 7: Secrets (credential management)
  ├── AWS Secrets Manager: master store
  ├── External Secrets Operator: syncs to K8s
  └── IRSA: no keys for AWS access — OIDC token exchange

Layer 8: Audit (what happened)
  ├── EKS audit logs → CloudWatch
  ├── DefectDojo: all scan findings centralized
  └── Grafana compliance dashboard: policy violations over time
```

## Layer 1: Secrets Management

### The Rule
"No hardcoded values. No keys. No PEM files. No passwords. No certificates. Everything must be dynamic and sourced from secrets."

### How It's Implemented

```
Developer workflow:
  ❌  password = "abc123"    → GitLeaks BLOCKS the commit
  ❌  AWS_KEY = "AKIA..."    → GitLeaks BLOCKS the commit
  ✓   password comes from ESO → K8s Secret → env var

Infrastructure:
  ❌  access_key = var.aws_key  → Terraform variables with secrets
  ✓   IRSA: pod gets temporary credentials via OIDC token exchange

CI/CD:
  ❌  AWS_ACCESS_KEY_ID stored in GitHub Secrets
  ✓   GitHub OIDC: CI job gets temp creds by assuming an IAM role
```

### AWS Secrets Manager Structure

```
intelliops/dev/
├── postgresql         → postgres_password, kong_password, sonarqube_password
├── grafana            → admin_password
├── argocd             → admin_password
├── defectdojo         → admin_password, secret_key, credential_aes256_key
├── sonarqube          → admin_password
├── backstage          → github_token
├── slack              → webhook_url
├── litmus             → mongodb_root_password, mongodb_root_user
├── linkerd            → ca_crt_b64, issuer_crt_b64, issuer_key_b64
└── falco-defectdojo   → api_key
```

**All values are generated by `install-stack.sh` Step 0** using `openssl rand -base64 32` — never hardcoded, never the same twice across deployments.

### External Secrets Operator Flow

```yaml
# ExternalSecret tells ESO: sync this SM path to a K8s Secret
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: grafana-secret
  namespace: monitoring
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager    # ClusterSecretStore
    kind: ClusterSecretStore
  target:
    name: grafana-credentials    # K8s Secret name to create
    creationPolicy: Owner
  data:
    - secretKey: admin-password  # K8s Secret key
      remoteRef:
        key: intelliops/dev/grafana    # SM path
        property: admin_password       # JSON field
```

**Check sync status:**
```bash
kubectl get externalsecret -A
# STATUS column: SecretSynced = good, SecretSyncError = check SM permissions
```

## Layer 2: Kyverno Policies

### How Kyverno Works

Kyverno is a MutatingAdmissionWebhook + ValidatingAdmissionWebhook. When any pod is created, Kubernetes sends the pod spec to Kyverno before allowing it. Kyverno evaluates policies and either:
- **Approves** the pod
- **Mutates** the pod (adds fields, changes values)
- **Blocks** the pod (returns 403 Forbidden)

### Policy 1: disallow-latest-tag

```yaml
# The problem: image: nginx:latest is non-deterministic
# Today it's 1.25.0. Tomorrow it might be 1.26.0 with breaking changes.
# You can't reproduce a deployment because "latest" moves.
```

**What's blocked:**
```yaml
containers:
  - image: nginx:latest          # BLOCKED
  - image: nginx                 # BLOCKED (same as :latest)
  - image: nginx:1.25.0          # ALLOWED
  - image: nginx:1.25.0@sha256:abc  # BEST — also pins digest
```

---

### Policy 2: disallow-privileged

```yaml
# Privileged containers have root access to the host kernel.
# A privileged container can:
#   - Mount any host filesystem path
#   - Load kernel modules
#   - Bypass all container isolation
# This is equivalent to running as root on the node.
```

**What's blocked:**
```yaml
containers:
  - securityContext:
      privileged: true           # BLOCKED
```

---

### Policy 3: disallow-host-namespaces

```yaml
# Host namespace sharing breaks container isolation.
hostPID: true     # See all processes on the node — trivial privilege escalation
hostNetwork: true # Bypass network policies — pod can reach any IP
hostIPC: true     # Share IPC namespace — can access shared memory of other processes
```

---

### Policy 4: require-pod-security-context

**What's required in apps namespace:**
```yaml
securityContext:
  runAsNonRoot: true     # Cannot run as UID 0
  runAsUser: 1000        # Must specify a non-root UID
  fsGroup: 1000          # File system group for volume access
```

Why UID 1000? The Dockerfiles create a user with `useradd -u 1000 -m app`. Kyverno verifies the pod runs as that non-root user.

---

### Policy 5: require-resource-limits

```yaml
# Without limits:
# - One buggy pod can consume 100% node CPU → all other pods starve
# - One memory leak can OOMKill the node → all pods on that node die
# This is a "noisy neighbor" problem.

containers:
  - resources:
      requests:         # Scheduling guarantee
        cpu: "100m"
        memory: "128Mi"
      limits:           # Hard cap — REQUIRED by Kyverno
        cpu: "500m"
        memory: "512Mi"
```

**Scope:** Enforced in `apps` namespace. Audited (not blocked) in `monitoring` — third-party charts can't always set limits.

---

### Policy 6: restrict-image-registries

```yaml
# Only images from our ECR registry are allowed.
# Blocks:
#   - Docker Hub images (potential supply chain attack)
#   - Unknown registries
#   - Typosquatted image names (imageName: nginx vs nignx)

allowedRegistries:
  - "*.dkr.ecr.us-east-1.amazonaws.com"
```

Combined with ECR's `ecr:PutImage` IAM restriction (only the CI OIDC role can push), this means only images built by our CI pipeline can run.

---

### Policy 7: verify-image-signatures

The most critical policy for supply chain security:

```yaml
verifyImages:
  - imageReferences:
      - "*.dkr.ecr.us-east-1.amazonaws.com/intelliops-dev/*"
    attestors:
      - keyless:
          subject: "https://github.com/nabilpurkar/intelliops-sherlock/.github/workflows/*"
          issuer: "https://token.actions.githubusercontent.com"
          rekor:
            url: https://rekor.sigstore.dev
```

**What this checks:**
1. Is there a Cosign signature attached to this image digest?
2. Was it signed by a GitHub Actions workflow from this specific repo?
3. Is the signature recorded in Rekor (public tamper-evident log)?

If any check fails → pod creation is blocked.

**IRSA requirement:** Kyverno needs to pull the signature from ECR to verify it. The Kyverno service account has an IRSA role with `ecr:GetDownloadUrlForLayer` permission.

## Layer 3: Falco Runtime Security

### What Falco Monitors

Falco uses eBPF to intercept Linux system calls. Every time a process:
- Opens a file (`open`, `openat`)
- Executes a program (`execve`)
- Makes a network connection (`connect`, `accept`)
- Changes privileges (`setuid`)

Falco evaluates these syscalls against its rule set in microseconds.

### Key Rules in This Platform

```yaml
# Detect a container spawning a shell — almost always an attacker
- rule: Terminal shell in container
  desc: A shell was spawned by a non-shell program in a container
  condition: >
    container and
    proc.name in (shell_binaries) and
    proc.pname not in (shell_binaries) and
    not proc.pname in (cron_binaries, alert_manager_binaries)
  output: "Shell spawned in container (user=%user.name container=%container.name)"
  priority: WARNING

# Detect reads of sensitive files
- rule: Read sensitive file
  desc: Attempt to read a sensitive file (passwd, shadow, etc.)
  condition: >
    open_read and sensitive_files and
    not proc.name in (safe_programs)
  output: "Sensitive file opened for reading (file=%fd.name container=%container.name)"
  priority: WARNING

# Detect writes outside of allowed directories
- rule: Write below etc
  condition: >
    open_write and
    fd.name startswith /etc and
    container
  output: "File below /etc opened for writing (file=%fd.name)"
  priority: ERROR
```

### Falco Alert Destinations

Alerts go to:
1. **Slack**: `intelliops/dev/slack` webhook URL — immediate notification
2. **Falco Sidekick** (optional): forwards to PagerDuty, OpsGenie, Datadog
3. **Prometheus**: Falco exposes alert count metrics — visible in the compliance dashboard

### Testing Falco

```bash
# This command will trigger the "Terminal shell in container" rule
kubectl exec -it -n apps deployment/order-service -- bash
# → Check Slack for the Falco alert
# → Check Grafana compliance dashboard for spike
```

## Layer 4: Linkerd mTLS

### What Is mTLS?

TLS (used in HTTPS) is one-way: the client verifies the server's certificate. mTLS (mutual TLS) is two-way: both sides verify certificates. This means:
- **Encryption**: All traffic between services is encrypted
- **Authentication**: The payment-service can verify "this request is from order-service, not from an attacker who got into the cluster"

### How Linkerd Implements It

```
order-service container
  └── sends HTTP request (unencrypted, to localhost)
      ↓
linkerd-proxy sidecar (same pod)
  └── intercepts outbound traffic
  └── performs TLS handshake with destination proxy
  └── presents its certificate (issued by Linkerd trust anchor)
      ↓ (encrypted mTLS connection)
linkerd-proxy sidecar (payment-service pod)
  └── verifies certificate
  └── decrypts traffic
  └── forwards to payment-service container (unencrypted, from localhost)
```

**The application containers see plain HTTP.** The proxies handle all TLS. Zero application code changes needed.

### Certificate Management

```
Linkerd trust anchor (root CA) — stored in SM: intelliops/dev/linkerd.ca_crt_b64
  └── Issues to: Linkerd issuer certificate
          └── Issues to: per-service leaf certificates (auto-rotated every 24h)
```

**Why store in Secrets Manager?** The trust anchor is the root of trust for all inter-service communication. If it's compromised, all mTLS is broken. Storing it in SM with IAM access control ensures only authorized systems can read it.

### Verifying mTLS

```bash
# Check that a connection is mTLS
linkerd viz edges deployment -n apps
# Shows: ORDER-SERVICE → PAYMENT-SERVICE (secured/meshed)

# Check all meshed pods
linkerd viz stat pod -n apps

# Tap live traffic (see headers, no body)
linkerd viz tap -n apps deployment/order-service
```

## Layer 5: cert-manager and TLS Certificates

### External TLS (Kong → Client)

The ACM wildcard certificate `*.yourdomain.com` terminates TLS at the ALB. All traffic from the internet is HTTPS — the browser-to-ALB connection is encrypted.

```
Browser → HTTPS → ALB (TLS termination with ACM cert)
                   → HTTP → Kong proxy
                           → HTTP → Services
```

**Why terminate at ALB and not at Kong?** ACM certificates are free and auto-renewed. ALB handles TLS at scale without overhead on the Kong pods.

### Internal TLS (cert-manager)

cert-manager manages certificates for:
- OTEL Operator admission webhook (requires valid cert for K8s webhook server)
- Any future internal HTTPS requirements

```bash
kubectl get certificates -A
kubectl get issuers -A
```

## Layer 6: EKS Security Hardening

### IMDSv2 Enforcement

The EC2 Instance Metadata Service (IMDS) provides temporary AWS credentials to running instances. IMDSv1 was vulnerable to SSRF (Server-Side Request Forgery) attacks:

```
1. Attacker finds an SSRF vulnerability in order-service
2. order-service makes a request to an attacker-controlled URL
3. Attacker redirects to: http://169.254.169.254/latest/meta-data/iam/security-credentials/
4. Gets the node's IAM role credentials
5. Can call any AWS API with node permissions
```

IMDSv2 requires a session token with a hop limit of 1 — containers cannot reach IMDS without a special header:

```hcl
# terraform/modules/eks/main.tf — Launch template
metadata_options {
  http_endpoint               = "enabled"
  http_tokens                 = "required"    # Force IMDSv2
  http_put_response_hop_limit = 1             # Pod can't reach IMDS
}
```

With IMDSv2 enforced, the SSRF attack vector is closed.

### EKS Audit Logging

All API server calls are logged to CloudWatch:
```
/aws/eks/intelliops-dev/cluster
  ├── api          — all kubectl/ArgoCD API calls
  ├── audit        — who did what to which resource, with outcome
  ├── authenticator — IAM and OIDC authentication events
  ├── controllerManager — deployment reconciliation
  └── scheduler    — pod scheduling decisions
```

**AWS Console:** CloudWatch → Log Groups → `/aws/eks/intelliops-dev/cluster`

## Layer 7: Network Policies

```yaml
# Example: apps namespace pods can only be reached by Kong and monitoring
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: apps-ingress
  namespace: apps
spec:
  podSelector: {}     # All pods in apps namespace
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kong
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: monitoring
```

This means order-service can't be reached directly from the internet or from other namespaces — traffic must go through Kong first.

## Interview Questions — Security & Compliance

**Q1: How do you enforce that only CI-built images run in production?**
> *Answer:* "Three layers working together. First, Kyverno's `restrict-image-registries` policy blocks any image not from our ECR registry. Second, ECR's repository policy restricts `ecr:PutImage` to only the GitHub Actions OIDC IAM role — developers can pull images but can't push. Third, Kyverno's `verify-image-signatures` policy verifies a valid Cosign keyless signature at pod admission time. The signature is scoped to our specific GitHub repo and workflow. An attacker who somehow gets ECR push access still can't produce a valid Cosign signature for our GitHub OIDC issuer. All three must fail for an unauthorized image to run."

**Q2: What is the security benefit of IRSA over node-level IAM roles?**
> *Answer:* "With node-level IAM roles, all pods on a node share the same credentials. If the ai-agent pod needs Bedrock access and order-service is on the same node, order-service also has Bedrock access. IRSA gives each pod its own scoped role: ai-agent gets Bedrock + SQS permissions, order-service gets nothing. The credentials are temporary OIDC-based tokens — they expire automatically and can't be shared. If a pod is compromised, the blast radius is limited to exactly what that pod's service account role allows, not the entire node's permissions."

**Q3: How does Falco differ from Kyverno in what it protects?**
> *Answer:* "Kyverno is a Kubernetes admission controller — it runs at pod creation time and enforces policies on the pod spec. It prevents misconfigured pods from starting. But once a container is running, Kyverno has no visibility. Falco runs inside the kernel and monitors system calls at runtime. If a container that passed all Kyverno checks later gets compromised and an attacker spawns a shell (`exec bash -i`), Kyverno never sees it — but Falco detects it within milliseconds via the `execve` syscall. Kyverno is pre-execution, Falco is runtime. You need both."

**Q4: Explain how Linkerd mTLS prevents a compromised pod from impersonating another service.**
> *Answer:* "Without mTLS, if an attacker compromises a pod in the monitoring namespace, they could make HTTP requests to order-service impersonating any identity. With Linkerd mTLS, every pod has a certificate issued by the Linkerd control plane's issuer CA. When monitoring pod A tries to connect to order-service, the Linkerd proxy on order-service validates the certificate. An attacker in monitoring namespace would need monitoring-namespace's certificate, not order-service's — so impersonation requires forging a certificate signed by the Linkerd trust anchor, which is only accessible via the Secrets Manager secret. The mTLS also encrypts all traffic, so a compromised node can't read traffic between other pods."

**Q5: A developer accidentally commits an AWS access key. Walk through exactly what happens.**
> *Answer:* "GitLeaks runs as stage 1 of every CI pipeline with `fetch-depth: 0` (full git history). It uses entropy analysis + pattern matching to identify the `AKIA...` key pattern. The CI job fails immediately — no subsequent stages run, no image is built. The developer gets a notification with the file and line number. The key is still in git history, so the next step is: 1) revoke the key immediately in IAM (don't wait for git history cleanup), 2) check CloudTrail for any API calls made with that key since the commit, 3) remove from git history with `git filter-branch` or BFG Repo Cleaner, 4) force push (with team sign-off), 5) add a `.gitleaks.toml` exception only if it was a test fixture with a deliberately fake key."
